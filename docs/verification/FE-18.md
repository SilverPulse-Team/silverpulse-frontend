Fecha de verificación técnica: 15 de noviembre de 2026.

## Resultado

| Criterio | Estado | Evidencia |
| --- | --- | --- |
| La importación usa el JSON del contrato y muestra el conteo devuelto | Cumple técnicamente | `ImportPage` entrega el `ImportRequest` construido en FE-17 a `DataProvider.importObservations`. `ImportResult` muestra `accepted`, `rejected`, `observation_ids` y `errors` sin recalcularlos. La prueba HTTP comprueba URL, método, `Content-Type` y body. |
| No se marca éxito con respuesta fallida | Cumple | El estado de resultado solo se crea cuando la promesa del provider termina correctamente. Respuestas HTTP 400, 409 y 422 lanzan `ApiClientError`, conservan estado/código/detalle y producen una vista de error con corrección o reintento. |
| No se realizan envíos duplicados por doble clic | Cumple | Los botones se deshabilitan y muestran estado de proceso. `createSubmissionLock` bloquea sincrónicamente una segunda ejecución antes del siguiente render; su prueba confirma una sola llamada mientras la primera está pendiente. |
| El usuario puede entender filas fallidas y corregirlas | Cumple | Los errores parciales muestran fila, código y detalle. Al corregir, se conservan solo las filas rechazadas cuando hubo aceptaciones parciales, evitando reenviar filas ya aceptadas. El error del backend vuelve a la tabla editable. |
| El dashboard/historial refleja la importación en modo HTTP operativo | Cumple en implementación; integración real pendiente | Después del POST se ejecuta `GET /ship/observations?astronaut_id=...`, se muestra el total actualizado y se ofrecen enlaces a historial/tendencias y panel. El provider mock demuestra la misma invalidación en memoria. No había FastAPI operativo en esta sesión para demostrar persistencia real. |

## Requerimientos demostrados

- Envío múltiple mediante `POST /ship/observations/import` con `application/json`.
- Captura individual mediante `POST /ship/observations` cuando existe exactamente una fila válida.
- Botones deshabilitados durante procesamiento, `aria-busy` y bloqueo síncrono independiente del render de React.
- Resultado con aceptados, rechazados, IDs de observación y errores detallados por fila.
- Manejo diferenciado de 400, 409 y 422, preservando el detalle real del backend.
- Un fallo HTTP o de red nunca produce el componente de resultado satisfactorio.
- Reintento disponible; errores corregibles regresan al mapeo de filas.
- Importaciones parciales filtran las filas aceptadas antes de una corrección posterior.
- Consulta de historial posterior al registro; un fallo del refresh se muestra separado del resultado del POST.
- El modo mock se identifica como `Resultado simulado · no persistido` y no se presenta como escritura en FastAPI/SQLite.
- El mock mantiene observaciones únicamente en memoria de su instancia y permite verificar el refresh sin fingir persistencia.
